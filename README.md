# THNP ClinicQ

ระบบนัดหมายและดูแลลูกค้าผ่าน LINE OA สำหรับคลินิกและร้านเสริมสวย

> แผนงานเต็มทั้ง 21 วันอยู่ที่ [docs/plan-clinic-demo.md](docs/plan-clinic-demo.md)

## ระบบนี้แก้ปัญหาอะไร

| ปัญหาของร้าน                          | สิ่งที่ระบบทำ                                                               |
| ------------------------------------- | --------------------------------------------------------------------------- |
| ลูกค้าลืมนัดแล้วไม่มา เสียคิวทั้งช่อง | เตือนล่วงหน้า 1 วันและก่อนถึงเวลา 2 ชั่วโมง พร้อมปุ่มยืนยัน/ขอเลื่อนใน LINE |
| มีคนยกเลิก คิวว่างแล้วปล่อยทิ้ง       | ส่งคิวว่างให้ลูกค้าที่รออยู่ทันที ใครกดก่อนได้ก่อน                          |
| ลูกค้าเก่าหายไปเฉย ๆ ไม่ได้ตามกลับ    | ตามลูกค้าที่ไม่มาเกิน 3 เดือนอัตโนมัติ พร้อมหน้าวัดผลว่าดึงกลับได้กี่คน     |
| คอร์สที่ขายไปหมดอายุโดยไม่ได้ใช้      | เตือนทั้งฝั่งลูกค้าและฝั่งร้านก่อนคอร์สหมดอายุ                              |

## เทคโนโลยีที่ใช้

| ส่วน      | เลือกใช้                                  |
| --------- | ----------------------------------------- |
| Backend   | NestJS 11 · TypeScript 5.9 (CommonJS)     |
| ฐานข้อมูล | PostgreSQL 17 · Prisma 7 (driver adapter) |
| คิวงาน    | BullMQ · Redis 7 _(เริ่มใช้ Phase 4)_     |
| Frontend  | Next.js 16 (App Router) · Tailwind CSS 4  |
| แจ้งเตือน | LINE Messaging API _(เริ่มใช้ Phase 3)_   |
| Monorepo  | pnpm workspace                            |

> **ทำไมถึงยังใช้ NestJS 11 ไม่ใช่ 12** — NestJS 12 เป็น ESM อย่างเดียว ซึ่งทำให้ Jest,
> decorator metadata และ Prisma client ที่ generate เป็น TypeScript ต้องตั้งค่าพิเศษหลายชั้น
> โปรเจกต์นี้เลือกความนิ่งของ CommonJS ไว้ก่อน เพราะปลายทางคือส่งมอบให้ลูกค้าดูแลต่อ

## เริ่มใช้งาน

ต้องมี **Node 20.19 ขึ้นไป** (ทดสอบบน 24.16), **pnpm** และ **Docker**

```bash
pnpm install                  # ติดตั้ง dependency ทั้ง workspace

cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env.local

pnpm db:up                    # เปิด PostgreSQL + Redis ด้วย Docker
pnpm db:migrate               # สร้างตารางในฐานข้อมูล
pnpm db:seed                  # ใส่ข้อมูลตัวอย่าง (ผู้ใช้ 3 สิทธิ์ ช่าง บริการ ลูกค้า 20 ราย)
pnpm dev                      # รัน backend + frontend + shared พร้อมกัน
```

### บัญชีสำหรับทดลองใช้

รหัสผ่านเดียวกันทุกบัญชีคือ `demo1234` — ตอนส่งมอบลูกค้าจริงต้องเปลี่ยนทั้งหมด

| อีเมล                  | สิทธิ์ | เห็นอะไร                                           |
| ---------------------- | ------ | -------------------------------------------------- |
| `owner@thnpclinic.com` | ADMIN  | ทุกอย่าง รวมถึงจัดการช่าง บริการ และปิดบัญชีลูกค้า |
| `staff@thnpclinic.com` | STAFF  | ข้อมูลลูกค้าครบ แต่แก้ช่างและบริการไม่ได้          |
| `demo@thnpclinic.com`  | VIEWER | ชื่อลูกค้าเท่านั้น ไม่เห็นเบอร์โทรและประวัติการมา  |

ลองเปรียบเทียบดูได้ที่ `/docs` — เข้าสู่ระบบด้วยคนละบัญชีแล้วเรียก `GET /api/customers`
จะเห็นว่า VIEWER ได้ข้อมูลกลับไปน้อยกว่าจริง ๆ ไม่ใช่แค่ถูกซ่อนที่หน้าจอ

จากนั้นเปิด:

| ที่อยู่                           | คืออะไร                       |
| --------------------------------- | ----------------------------- |
| http://localhost:3000             | Dashboard                     |
| http://localhost:3001/api         | API                           |
| http://localhost:3001/docs        | เอกสาร API (Swagger)          |
| http://localhost:3001/health/deep | สถานะระบบพร้อมผลตรวจฐานข้อมูล |

## โครงสร้างโปรเจกต์

```
backend/          NestJS API
  prisma/         schema + migration
  prisma.config.ts  ตั้งค่า Prisma CLI (Prisma 7 ย้าย url มาไว้ที่นี่)
  src/
    common/       exception filter, utility ที่ใช้ร่วมกัน
    config/       ตรวจ env ตอน boot
    health/       endpoint ตรวจสถานะระบบ
    prisma/       PrismaService
    generated/    Prisma client (สร้างอัตโนมัติ — ไม่ต้องแก้)

frontend/         Next.js dashboard
  src/app/        หน้าเว็บ (App Router)
  src/components/ คอมโพเนนต์
  public/brand/   โลโก้

shared/           โค้ดที่ backend กับ frontend ใช้ร่วมกัน
  src/brand.ts    สีแบรนด์ (วัดจากไฟล์โลโก้จริง)
  src/enums.ts    enum + ป้ายภาษาไทย
  src/api.ts      รูปแบบ response และรหัส error

docs/             เอกสารแผนงานและข้อมูลขายงาน
```

## หมายเหตุเรื่อง PDPA

ข้อมูลลูกค้าคลินิกเป็นข้อมูลส่วนบุคคลที่อ่อนไหว ระบบนี้จึงออกแบบโดย:

- **ไม่มีที่เก็บรายละเอียดการรักษาเลยตั้งแต่ระดับ schema** — ข้อความที่ส่งออกจึงสะอาดโดยโครงสร้าง ไม่ต้องพึ่งวินัยของคนกรอก
- **แยกความยินยอมเป็น 2 ชนิด** (รับการเตือนนัด / รับข้อความการตลาด) พร้อมบันทึกเวลาที่ให้ความยินยอม
- **บันทึกแม้ตอนที่ระบบเลือกไม่ส่ง** — `MessageLog` เก็บเหตุผล เช่น ยังไม่ได้ให้ความยินยอม เพื่อให้ตรวจสอบย้อนหลังได้
- **แบ่งสิทธิ์ 3 ระดับ** — ระดับ VIEWER เห็นตารางนัดได้แต่ไม่เห็นข้อมูลติดต่อลูกค้า
